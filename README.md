# Notification System — Technical Specification
## 1. Overview

This document specifies the architecture for a multi-channel notification system (Push, SMS, Email) designed to serve 1M+ users reliably. The system guarantees no duplicate sends, no missed sends, and graceful degradation when third-party providers fail.

---

## 2. Requirements

### Functional
- Send notifications via three channels: Push (FCM/APNs), SMS (Termii/Twilio), Email (SendGrid/Mailgun)
- Support transactional notifications (OTP, withdrawal alerts, trade confirmations)
- Support marketing/bulk notifications (campaigns, announcements)
- Allow per-user channel preferences and opt-outs
- Provide delivery status tracking per notification

### Non-Functional
- **Throughput:** 50,000+ notifications/minute at peak
- **Latency:** Transactional notifications delivered < 5 seconds end-to-end
- **Durability:** Zero message loss — every triggered notification must be sent or explicitly failed after retries
- **Deduplication:** The same notification must never be delivered twice to the same user
- **Availability:** 99.9% uptime on the notification service itself, independent of provider uptime

## 4. Core Components

### 4.1 Notification API

Single entry point for all upstream services. Accepts notification requests and returns immediately after writing to the queue — fire and forget from the caller's perspective.

**Endpoint:**
```
POST /v1/notifications
```

**Request payload:**
```json
{
  "idempotency_key": "trade_confirm_user_123_txn_456",
  "user_id": "usr_abc123",
  "type": "TRADE_CONFIRMATION",
  "priority": "HIGH",
  "channels": ["push", "email"],
  "data": {
    "title": "Trade Confirmed",
    "body": "Your ₦50,000 investment in Cowrywise Flex Dollar was successful.",
    "metadata": {
      "transaction_id": "txn_456",
      "amount": 50000
    }
  },
  "scheduled_at": null
}
```

**Response:**
```json
{
  "notification_id": "ntf_789xyz",
  "status": "QUEUED",
  "idempotency_key": "trade_confirm_user_123_txn_456"
}
```

The API does three things and nothing else:
1. Validates the request
2. Checks idempotency (reject or return existing result if duplicate)
3. Writes to the message queue

---

### 4.2 Idempotency Layer

Every notification request carries an `idempotency_key` generated by the caller. This is the primary defence against duplicates.

**Flow:**
```
1. Request arrives with idempotency_key
2. SET NX (set if not exists) in Redis:
      key:   idempotency:{idempotency_key}
      value: {notification_id, status, created_at}
      TTL:   24 hours

3. If SET NX returns OK → new request, proceed to queue
4. If SET NX returns nil → duplicate, return original notification_id immediately
```

**Redis command:**
```
SET idempotency:trade_confirm_user_123_txn_456
    '{"notification_id":"ntf_789xyz","status":"QUEUED"}'
    EX 86400
    NX
```

This is atomic — no race conditions. Two simultaneous requests with the same key: one wins, one gets the cached result.

**Idempotency key format (enforced by callers):**
```
{event_type}_{user_id}_{source_entity_id}

Examples:
  trade_confirm_usr123_txn456
  otp_login_usr123_req789
  withdrawal_alert_usr123_wd101
```

### 4.3 Message Queue Design

**Technology:** RabbitMQ (self-hosted) or AWS SQS (managed)

**Queue topology — separate queues by priority and channel:**

```
notifications.high.push     ← OTPs, security alerts, trade confirms
notifications.high.sms
notifications.high.email

notifications.normal.push   ← Portfolio updates, general alerts
notifications.normal.sms
notifications.normal.email

notifications.bulk.push     ← Marketing campaigns, announcements
notifications.bulk.sms
notifications.bulk.email

notifications.dlq           ← Dead letter queue (all failed messages)
```

**Why separate queues by priority:**
A marketing blast to 1M users must not block OTP delivery. Separating queues means HIGH priority workers always have CPU and throughput available regardless of bulk queue depth.

**Queue configuration:**
```
Message TTL:         24 hours (HIGH), 72 hours (NORMAL), 7 days (BULK)
Max delivery count:  5 attempts before DLQ
Visibility timeout:  30 seconds (prevents duplicate processing if worker crashes)
```

### 4.4 Channel Workers

One worker pool per channel. Workers are stateless and horizontally scalable.

**Worker processing loop:**
```python
def process_notification(message):
    notification = deserialize(message)

    # Step 1 — Check if already delivered (worker-level dedup)
    if delivery_log.exists(notification.id, notification.channel):
        message.ack()
        return

    # Step 2 — Mark as IN_PROGRESS (prevent concurrent duplicate sends)
    lock_key = f"sending:{notification.id}:{notification.channel}"
    if not redis.set(lock_key, 1, nx=True, ex=30):
        # Another worker is already processing this — skip
        message.nack(requeue=False)
        return

    # Step 3 — Check user preferences
    if not user_prefs.channel_enabled(notification.user_id, notification.channel):
        delivery_log.record(notification.id, notification.channel, "OPT_OUT")
        message.ack()
        return

    # Step 4 — Send via provider
    result = provider_router.send(notification)

    # Step 5 — Record result
    delivery_log.record(notification.id, notification.channel, result.status)

    # Step 6 — Ack only on success or permanent failure
    if result.status in ["DELIVERED", "PERMANENTLY_FAILED"]:
        message.ack()
    else:
        # Transient failure — nack so queue retries
        message.nack(requeue=True)
```

**Critical: message is only ACKed after delivery is confirmed and logged. If the worker crashes between send and ack, the queue redelivers — the worker-level dedup check in Step 1 catches this and skips the re-send.**

### 4.5 Provider Router — Graceful Degradation

Each channel has a primary provider and at least one fallback. The router handles failover automatically.

**Circuit breaker per provider:**
```
States: CLOSED → OPEN → HALF_OPEN → CLOSED

CLOSED:     Normal operation — all requests go through
OPEN:       Provider is failing — route to fallback immediately
HALF_OPEN:  Test one request — if success, close; if fail, stay open

Thresholds:
  Open circuit after:    5 failures in 60 seconds
  Half-open after:       30 seconds in OPEN state
  Close after:           3 consecutive successes in HALF_OPEN
```

**Provider routing logic:**
```python
class ProviderRouter:

    PROVIDERS = {
        "push":  [FCMProvider, OneSignalProvider],
        "sms":   [TermiiProvider, TwilioProvider, InfobipProvider],
        "email": [SendGridProvider, MailgunProvider, AWSSESProvider],
    }

    def send(self, notification):
        providers = self.PROVIDERS[notification.channel]

        for provider in providers:
            circuit = self.circuit_breaker(provider)

            if circuit.is_open():
                # Provider is failing — try next
                metrics.increment(f"provider.{provider.name}.skipped_open_circuit")
                continue

            try:
                result = provider.send(notification)
                circuit.record_success()
                return result

            except ProviderRateLimitError:
                circuit.record_failure()
                continue   # try next provider

            except ProviderUnavailableError:
                circuit.record_failure()
                continue   # try next provider

            except PermanentDeliveryError as e:
                # e.g. invalid phone number — no point trying other providers
                return DeliveryResult(status="PERMANENTLY_FAILED", reason=str(e))

        # All providers exhausted
        return DeliveryResult(status="ALL_PROVIDERS_FAILED")
```

**Provider-specific failure handling:**

| Failure Type | Example | Action |
|---|---|---|
| Rate limit (429) | Twilio throttling | Circuit break, try fallback |
| Service unavailable (503) | SendGrid outage | Circuit break, try fallback |
| Invalid recipient | Bad phone number | Permanently fail, do not retry |
| Auth error (401) | Expired API key | Alert on-call, circuit break |
| Timeout | No response in 10s | Circuit break, try fallback |
| All providers down | Mass outage | Park in DLQ, page on-call |

### 4.6 Delivery Tracking

Every send attempt — success or failure — is written to the delivery log.

**Schema:**
```sql
CREATE TABLE notification_events (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    notification_id UUID NOT NULL,
    user_id         UUID NOT NULL,
    channel         VARCHAR(10) NOT NULL,    -- push, sms, email
    provider        VARCHAR(30) NOT NULL,    -- fcm, termii, sendgrid
    status          VARCHAR(20) NOT NULL,    -- QUEUED, SENT, DELIVERED,
                                             -- FAILED, OPT_OUT, DUPLICATE
    provider_ref    VARCHAR(255),            -- provider's message ID
    error_code      VARCHAR(50),
    error_message   TEXT,
    attempted_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    delivered_at    TIMESTAMPTZ
);

CREATE INDEX idx_notif_events_notification ON notification_events (notification_id);
CREATE INDEX idx_notif_events_user_channel ON notification_events (user_id, channel, attempted_at DESC);
```

**Provider webhooks update delivery status:**

Providers like SendGrid and Twilio send delivery receipts via webhooks. A webhook handler updates `delivered_at` and sets status to `DELIVERED` or `BOUNCED`.


### 4.7 Dead Letter Queue (DLQ) Handler

Messages that exhaust all retries land in the DLQ. This is not a graveyard — it is a work queue for the ops team.

**DLQ processor runs every 15 minutes:**
```python
def process_dlq():
    messages = dlq.poll(limit=100)

    for message in messages:
        notification = deserialize(message)

        # Was this eventually delivered via another channel?
        if delivery_log.any_channel_delivered(notification.id):
            message.ack()   # Already reached user, discard
            continue

        # Classify the failure reason
        if notification.type in CRITICAL_TYPES:  # OTP, security alert
            ops_alert.page_oncall(notification)
            retry_with_all_providers(notification)
        else:
            ops_alert.create_ticket(notification)
            delivery_log.mark_final_failure(notification)
```

**Critical notification types** (OTP, security alerts, withdrawal confirmations) trigger an on-call page. Non-critical failures (marketing emails) create a ticket for next-day review.

## 5. Deduplication — Full Strategy

Three independent layers ensure a notification is never sent twice:

```
Layer 1 — API level:
  Redis SET NX on idempotency_key
  Catches: duplicate requests from upstream services

Layer 2 — Worker level:
  Check delivery_log before sending
  Distributed lock during send (Redis NX, 30s TTL)
  Catches: message redelivery after worker crash

Layer 3 — Provider level:
  Pass notification_id as provider idempotency header
  e.g. SendGrid: X-Message-Id header
  Catches: duplicate sends if worker retries after provider timeout
```

**What Layer 2 specifically protects against:**

If a worker sends the notification, the provider delivers it, but then the worker crashes before ACKing the queue message — RabbitMQ redelivers the message to another worker. Without Layer 2, the user gets the notification twice. The delivery log check at the top of the worker loop catches this and ACKs the message without re-sending.

## 6. Bulk Notification Flow (1M+ Users)

Marketing campaigns and system-wide announcements require a different approach from transactional notifications.

```
1. Campaign created via admin API
   {type: "CAMPAIGN", segment: "all_users", template_id: "t_123", scheduled_at: "..."}

2. Campaign Scheduler triggers at scheduled_at

3. User Segment Resolver:
   SELECT user_id FROM users
   WHERE opted_in_marketing = true
   AND channel_push_enabled = true
   LIMIT in batches of 1,000

4. For each batch:
   - Render template per user (personalisation)
   - Write batch to notifications.bulk.push queue
   - Rate: 10,000 messages/second queue write throughput

5. Bulk workers consume at controlled rate:
   - Respect per-provider rate limits (FCM: 500k/min, Termii: varies by plan)
   - Use token bucket rate limiter per provider

6. Progress tracked in Redis:
   campaign:{id}:total    = 1,000,000
   campaign:{id}:sent     = 847,293   (incremented atomically)
   campaign:{id}:failed   = 1,204
   campaign:{id}:status   = "IN_PROGRESS"
```

**Estimated time to send 1M push notifications:**
At FCM's limit of ~500k/min, a 1M push campaign completes in ~2 minutes using 4 bulk worker instances.

## 7. User Preferences

Every send checks preferences before touching a provider:

```sql
CREATE TABLE user_notification_preferences (
    user_id         UUID PRIMARY KEY,
    push_enabled    BOOLEAN DEFAULT true,
    sms_enabled     BOOLEAN DEFAULT true,
    email_enabled   BOOLEAN DEFAULT true,
    quiet_hours_start TIME,              -- e.g. 22:00
    quiet_hours_end   TIME,              -- e.g. 07:00
    timezone          VARCHAR(50) DEFAULT 'Africa/Lagos',
    marketing_push    BOOLEAN DEFAULT true,
    marketing_sms     BOOLEAN DEFAULT false,
    marketing_email   BOOLEAN DEFAULT true,
    updated_at        TIMESTAMPTZ DEFAULT now()
);
```

Preferences are **cached in Redis** with a 5-minute TTL. Transactional notifications (OTP, security alerts) bypass quiet hours and marketing opt-outs — they always send.

## 10. Failure Mode Summary

| Scenario | Behaviour |
|---|---|
| Primary SMS provider down | Circuit opens → route to fallback automatically |
| All SMS providers down | Message stays in queue, DLQ after 5 retries, ops alerted |
| Worker crashes mid-send | Queue redelivers, worker dedup layer skips re-send |
| Duplicate API request | Idempotency layer returns original result, nothing queued |
| Database slow | Preference cache absorbs read load, writes async |
| Redis down | Idempotency degrades gracefully — log warns, still sends |
| 1M user campaign spike | Bulk queue isolated from transactional, rate limited per provider |
| Invalid phone number | Permanently failed immediately, no retry, log records reason |
